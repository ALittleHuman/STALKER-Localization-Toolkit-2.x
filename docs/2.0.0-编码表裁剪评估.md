# 2.0.0 编码表裁剪评估（用户 2026-09-26 要求"评估后给结论"）

> 背景：用户 2026-09-26 决策第 ④ 条 —— **日文砍掉；原文（源文本）字符范围只考虑西里尔 + 西欧
> （含英文）**，并留了一句："编码链/编码表是否相应裁剪（gb18030 在 A 链的位置、gbk/gb2312 表
> 去留），由你评估后给结论。" 本文就是那个结论 + 依据。

## 1. 先看这些表**实际用在哪**（不是"看起来像中文相关"就裁）

| 使用点 | 位置 | 用途 |
|---|---|---|
| A 链（读源文本） | `engine::text::read_text_file` 六编码链：utf-8(-sig) / gb18030 / gbk / gb2312 / cp1251 / cp1252 / latin-1 兜底 | 解包出来的**源文件**解码 |
| B 链第 4 步 | `sniff.cpp` 的"XML 声明被字节证实"（`gb2312`/`gbk`/`gb18030` 声明） | 编码转换页 |
| 字库字符集 | `extract_chars` 递归读文本收集字形（**含 GBK 源**） | 汉化包生成 |
| 有损编解码 | `encoding.cpp` 的 gb 两字节路径 + gb18030 四字节路径 | 编码转换页 |

## 2. 证据（已有、可复跑）

1. **真机语料里没有中文编码的源**：`tests/golden_text_decode.py` 的语料（6 棵树各 30 文件，
   绝对路径写在 `tests/golden/text_decode.json`）实测编码形态＝ **ascii / cp1251 / utf-8 混布，
   没有 gb18030 真样本**；判定链实测（`_2x_ref/sniff_probe.py`，真语料 300 文件）胜出步频次
   ＝ BOM 16 / 多字节 UTF-8 4 / XML 声明 78 / chardet 146（其中 144 次判 ascii）/ 默认 cp1251 56。
2. **但"译文"这一侧不能一刀切**：我方字库/字符集工作里**真踩过 GBK 源**（`extract_chars` 对
   GBK 源静默丢字，实测 11 字全丢 —— 已修），中文汉字**既可能以 GBK/GB2312 存储**（中文模组
   常见），也可能 UTF-8。B 链第 4 步的 `gb2312` 解码表就是为"声明了 gb2312 的 XML"补的
   （补之前字库字符集少 6 个汉字）。
3. 裁表的**收益**很小：几张 `.inc` 表合计体积在百 KB 级、只在解码路径上按需查表；而裁错的
   代价是**静默丢字/乱码**（第 2 条就是实例）。

## 3. 结论（不裁表，但把"范围"落到该落的地方）

- **不删 gb18030 / gbk / gb2312 三张表**。理由：① 用户限定的是"**原文**只考虑西里尔+西欧"，
  而这三张表还服务**译文侧**（中文模组的 GBK/GB2312 存储）与 B 链的**声明证实**；② 收益（体积）
  远小于风险（丢字/乱码）；③ 它们是**数据表**，不引入启发式、不改变判定逻辑。
- **落实"原文只考虑西里尔+西欧"的正确位置**是**判定链第 5 步（chardet 家族）**：
  既然原文不会出现 GBK/Big5/Shift-JIS 源 ⇒ **确定不做**（此前是"记账"，现在是"按用户范围
  不做"）。差异台账里那 5 条 chardet 家族条目随之定性为"**范围外**"，保留在案以防回归。
- **触发复评的条件**（写下来，免得日后拍脑袋）：若将来出现"**译文一律 UTF-8**"的明确口径，
  或出现"只处理 UTF-8/cp1251 源"的发行形态，再评估裁表；届时判据＝对真语料跑一遍
  `golden_text_decode` + 字库 `extract_chars`，确认没有文件走 gb 表仍有正确输出。
- **不动 ⑨9.7/⑥6.x 那几条锁**：`lossy_encodings()` 下拉只列做过对拍的编码这条纪律不变
  （utf-16/32 有损仍在待补清单里，补完才进下拉）。

## 5. 补记（2026-10-05 D3 批）：big5 / shift_jis / euc-kr 三张表已补

用户 2026-10-05 裁决「**这个编码表，补起来也不麻烦，顺手补上就是了。**」⇒ 本文第 3 节
"第 5 步 chardet 家族**确定不做**"的结论**不变**（那是**判定链的统计探测**，不移植 chardet），
但**三张表本身**补上了：解码 + 编码两侧、与 Python 同名 codec 逐字节对拍
（`tests/golden_lossy_codec.py`），并进编码转换页的源/目标下拉。

- 三张表的**用途**与 gbk/gb2312 同族：服务"**译文侧**可能出现的东亚编码文件名/正文"
  与用户**手动指定**（1.x 的 `ENCODING_CHOICES` 源侧本来就有这三个名字）；
- **判定链**（B 链第 5 步）仍然**不**用它们 —— 没移植 chardet，`sniff.cpp` 的
  `BYTE_DECODE_CANDIDATES` 也没加它们 ⇒ `tests/golden_text_sniff.py` 的差异台账不动
  （这是**故意**的，不是漏做）；
- 实测语义与判据见 `docs/2.0.0-文本模块规格.md` §5.4。
