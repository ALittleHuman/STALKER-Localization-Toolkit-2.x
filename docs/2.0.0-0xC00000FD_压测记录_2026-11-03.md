## 更正：0xC0000409 是「已规避」，不是「已归因修复」（DSH 2026-11-03）

早前写的是"根因是 C++ 在 GIL 块里迭代 `py::object` 拼列表 ⇒ 0xC0000409"。**这个机制不成立**：
持有 GIL 时迭代一个合法的 `py::list` 是标准操作，不会触发 `STATUS_STACK_BUFFER_OVERRUN`
（0xC0000409 是 `__fastfail`，通常来自 `/GS` 栈 cookie 被破坏、`abort()`、
CRT invalid parameter handler、或 pybind11 internals 存在两份）。

⇒ 准确表述：

```
0xC0000409：已规避（C++ 不再迭代 py::object 拼列表，改 Python 侧拼接），**未归因**。
不可作为"0xC00000FD 与它无关"的证据 —— 两起 fail-fast 可能同源（栈破坏是共同上游）。
下次任何 fail-fast（0409/00FD/0005）都先 !analyze -v 看 exception code + 栈，不先归因。
```

## 附：一次"环境假红"（杀软，2026-11-04 21:1x）

**现象**：所有 GUI exe（含**已验证过**的 BETA.107 旧包）`exit 1` + stdout/stderr 全空；
`procdump` 报 `Access is denied`；重链、`QT_QPA_PLATFORM=offscreen`、`Start-Process -RedirectStandard*`、
`cmd /c` 全无效。21:3x 自行恢复，`SHELL-SMOKE ok checks=961`。

**归因（用户 2026-11-04 确认）**：**杀软**拦截了程序化启动的 `xrkit_app.exe`；手动双击/命令行启动正常。

**纪律**：
- 这类"零输出 + 立刻退出 + 连旧包一起坏"是**环境红**，不要当成 0xC00000FD / 0xC0000409 的证据；
- 判据：同一份 exe **手动能跑、门禁里跑不了** ⇒ 先怀疑杀软/会话，再怀疑代码；
- `procdump` 也被拒时，不要反复重试到刷屏，直接记环境红并重跑一次。

## ★ 归因：0xC00000FD 是 **cmake 的整文件正则**，不是 xrkit_app（2026-11-05）

### 复现（最小）

```cmake
# probe.cmake
file(READ ".../tools/cli/main.cpp" content)          # 389 KB
string(REGEX REPLACE "/\\*([^*]|\\*[^/])*\\*/" "" content "${content}")
string(REGEX REPLACE "//[^\n]*" "" content "${content}")
```

```
cmake -P probe.cmake
⇒ exit = -1073741571（0xC00000FD STATUS_STACK_OVERFLOW），**无任何输出**
```

### 为什么它会出现在门禁里

`cmake/check_no_qt.cmake`（J5：core/engine/CLI 不许含 Qt）用**整文件**正则剥注释。
`tools/cli/main.cpp` 长到 389 KB 后，CMake 的 regex 递归实现爆栈 ⇒ J5 这一步崩溃
⇒ 构建失败、错误信息为空（只有退出码）——**与 xrkit_app 崩溃长得一模一样**，
过去被误记为"产品栈溢出"。

### 修法

`check_no_qt.cmake` 改成**逐行**剥注释（块注释用状态机、行注释用短正则），
不再让 regex 递归整文件：

```
cmake -P cmake/check_no_qt.cmake
⇒ -- J5 OK：119 个 core/engine/公共头文件均无 Qt 依赖   exit=0
```

### 口径

- **0xC00000FD 不再"未归因"**：至少存在一个已证实的来源（cmake 整文件正则）；
- 但**不等于**"产品侧的栈溢出已排除"：`xrkit_app` 自身的 0xC00000FD 仍可能另有来源，
  下次真崩溃仍按 procdump 抓栈；
- 纪律不变：这条归因只覆盖"构建/门禁里那次 0xC00000FD"，不要拿它解释产品运行时崩溃。
