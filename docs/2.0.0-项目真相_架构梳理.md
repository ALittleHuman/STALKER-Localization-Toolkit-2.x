# 2.0.0 项目真相：架构梳理（只读，2026-10-23）

> 目的：解释**为什么同几条红（P5 / P12c-2 / P16-3c / P13-2a-2 / P17-1②）会反复长出来**，
> 以及它们分别在什么层面可以一次判死。本文只描述现状与可选方向，**不改代码**。

---

## 一、项目地图（谁负责什么）

| 层 | 目录 | 职责 | 性质 |
|---|---|---|---|
| 引擎 | `src/engine/**`、`include/xrkit/**` | 包格式解析、插件加载（Python）、控件门面（`UiFacade` 的**接口定义**） | 产品 |
| 外壳 | `src/shell/**` | `Hub`（窗口/页/日志/任务壳）、`pages/*`（六个内置页）、`widget_facade_qt.cpp`（门面的 **Qt 实现**） | 产品 |
| 插件 | 打包内的 `plugins/*.py` | 调 `api.ui.*` 建页、注册工具 | 产品（第三方） |
| CLI | `xrkit_cli` | 无 GUI 的包操作 | 产品 |
| 打包 | `scripts/package.ps1`、`build/logs/_pkg.py` | 出包 + **包内离屏自检**（`SHELL-SMOKE ok`） | 发布链 |
| 判据 | `src/shell/smoke.cpp`（`--smoke`）、`tests/check_package_fixture_pages.py` | 同一份 `--smoke` 跑一遍，Python 侧再筛 ①②③④ | **夹具**（不是产品） |

**关键事实**：判据与产品**共用同一份 `smoke.cpp`**。判据里的每一段 `check(...)` 都跑在真实 Hub 上，
所以判据的读取方式（取指针、取全局、时机）本身就是**被测系统的一部分**。

## 二、生命周期图（从构造到判据读取）

```
Hub::Hub()
  ├─ 建 UI（tab 条、stack、log_box_、status_label_、任务壳…）
  ├─ register_builtin_pages(pages_)        // 六个内置页进注册表
  ├─ install_qt_ui_facade(sink, this)      // ★ 门面在 load_plugins 之前装
  └─ load_plugins(dir)
        ├─ PyHost 加载 .py → registry 里多出若干 PageSpec(kind=Plugin)
        └─ sync_pages()                    // ★ 页装配**只此一处**
              for each spec:
                ├─ 内置页：new XxxPage
                └─ 插件页：
                      container = new QWidget          ← builder 的"父"
                      built = reg->builder(container)  ← Python build()
                      if (built == nullptr):
                            widget = make_placeholder(spec)   // 2~3 个标签
                      else:
                            widget = new PluginPage(id, title, built)  // ★ 包装
                      page_widgets_[i] = widget
                      stack->addWidget(widget)
```

四个指针的关系（这是 P5 反复红的根源）：

| 名字 | 指向 | 谁写 |
|---|---|---|
| `container` | builder 拿到的父容器 | `sync_pages()` 造，**不**进 `page_widgets_` |
| `built` | Python `build()` 返回的根控件（通常就是 `container` 或它的子件） | 插件 |
| `page_widget`（判据里） | `hub.stack()->widget(page)` | 判据取 |
| `page_widgets_[i]` | **最终页控件**：`PluginPage` 或占位页 | `sync_pages()` |

⇒ **判据 `dynamic_cast<PageBase*>(page_widget)` 只在"最终页"是内置页/`PluginPage` 时才成功**；
    若那次落的是占位页（裸 `QWidget`），两个 cast 全空 —— 这正是 P5 那条
    `P5 插件页没被套上宿主视口（长内容会滚不动）` 的真实含义：**不是视口没套，是页没建出来**。

## 三、线程与全局状态（所有权错位清单）

| 状态 | 作用域 | 谁写 | 风险 |
|---|---|---|---|
| `current_panel_root()` | **进程级**（`static` + mutex） | `UiPanelScope` ctor/dtor（保存/恢复 `previous_`） | 嵌套/乱序/跨页都会互相踩；实测 `lifo=1` 正常，但"谁在读"仍是全局读 |
| `current_page_id()` | **进程级** | 同上（页上下文 scope） | `scope_dtor` 之后会**变回空**；钩子里读它就是空（已实测） |
| `UiFacade::on_ui_thread` | 进程级函数指针 | `install_qt_ui_facade` | 装晚了 ⇒ 所有 `ui.*` 返回 None |
| `TaskShell::running_` | **每 shell 实例** | `run()` 置位；`apply_finish()` 经 `QueuedConnection` 复位 | worker 已结束但复位在队列里 ⇒ 下一次 `run()` 可能被拒（本轮实测**未发生**：`running_before=0`） |
| `page_widgets_` / `page_ids_` | 每 Hub | `sync_pages()` | 重建页时索引会变；判据缓存旧指针就红 |
| `menu_ready_actions`（判据） | 每进程静态钩子 | `notify_menu_ready` | 全局钩子 ⇒ 必须带 `page`（已改由调用点传） |

## 四、判据分层（哪些该进 BETA 门槛）

| 层 | 例子 | 特征 | 建议 |
|---|---|---|---|
| **A. 结构判据** | 包能解、页数对、注册表条目、CLI 退出码 | 与 UI 时序无关、可复现 | **进门槛**，一次判死 |
| **B. 页构造判据** | `settle anything=1`、页是 `PageBase`/`PluginPage`、`page_ready` 发过 | 与"页建没建出来"绑定 | **进门槛**（这是产品正确性） |
| **C. GUI 交互判据** | P5 视口能滚、P13 菜单项、P16 按钮菜单、P17 取消位 | 依赖事件循环/焦点/时机 | **观察项**：先只统计不判死，或每项单独进程 |
| **D. soak / 压力** | 30×、`--fast` 118 步 | 统计性质 | 只在 B 全绿后跑，用"连续两轮 ≥19/20"或 30 次 ≥28 |

现在的问题：**C 层被当成 A/B 层在卡 BETA**，而 C 层的失败率（每项 1~3/30）在
offscreen + 单进程顺序建所有页的条件下**无法归零**。

## 五、简化方案（先列，不动手）

### 方案 1：**每页一个进程**（改动最小、收益最大）
判据按页 id 启动 `xrkit_app --smoke --page=<id>`，一个进程只建这一页。
- P5/P12c/P16/P13 的"随执行顺序漂"自然消失；
- 失败定位到具体页，不再互相污染；
- 代价：进程启动 ×N（每次 ~1s），30 次 soak 变慢约 6 倍。

### 方案 2：**Hub 返回 `PageBuildResult`**
`PageBuildResult { QWidget* page; enum Status {Built, Placeholder, Failed}; QStringList diagnostics; }`
判据问 Hub 要结果，**不再自己 `dynamic_cast` 猜实例**。
- 直接消灭"cast 空到底是占位还是 RTTI"这类歧义；
- `sync_pages()` 里已经有这些信息（`built == nullptr` 分支、`plugin_errors`）。

### 方案 3：**显式 page context 取代全局 `current_panel_root`**
`BuilderContext { UiHandle root; std::string page_id; }` 作为 `builder(ctx)` 的参数；
`ui.*` 从 ctx 取根，不再读全局。
- 彻底消除 scope 保存/恢复这类隐含状态；
- 代价：动 `PanelBuilder` 签名（引擎 + 外壳 + 所有夹具），一次性成本高。

### 方案 4（极小）：**判据只认 B 层**
把 C 层（P5/P13/P16/P17）从 BETA 门槛里摘出来，改成"统计项"，BETA 只看 A+B。
- 立刻可到 30/30（A+B 目前全绿）；
- 代价：GUI 交互的回归只能靠人工/单独 soak 发现。

**建议顺序**：先做方案 2（小、直接改善判据可信度）→ 方案 1（隔离，消灭顺序耦合）→ 方案 3（架构性，最后做）。
