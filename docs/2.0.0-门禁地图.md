## 一、基础设施与语义

### 1.1 三个档位（`main()` 7296-7297）

| 档 | 含义 | SKIP 的后果 | 未覆盖清单的后果 |
|---|---|---|---|
| `--fast` | 公开 CI：跳过外部前提步骤 | 记 SKIP + `UNCOVERED` | **不判红**（结论行如实说"本次未覆盖"） |
| 默认（local） | 能跑的都跑 | 记 SKIP + `UNCOVERED` | 不判红 |
| `--release` | 发版口径 | `prereq()` 直接 `fail()`（**零容忍**） | `UNCOVERED` 非空 ⇒ 收尾整体 FAIL（7378-7380） |

### 1.2 五类"状态产生器"（都在顶部 149-200）

| 函数 | 写什么 | 性质 | release 档 |
|---|---|---|---|
| `fail(msg)` | `FAILURES += 1` | 真失败 | FAIL |
| `ok(msg)` | 只打印 | 通过 | — |
| `prereq(what, why, release)` | `UNCOVERED`（或 release 时 `fail`） | **外部前提缺件**（参照工具/真机样本/包不存在） | **FAIL** |
| `ledger(what, why)` | `LEDGERS` | **已知且被冻结的能力缺口**（如 chardet GB2312 探针未移植） | **不阻断**，但必须可见 |
| `package_fact(what, why, release)` | release: `prereq`；其它: `ledger` | 包内端到端事实 | **不许退化为台账**（P17-2） |

★★ 关键判据（P17-2，185-199）：**`LEDGERS` 不进 `UNCOVERED`** ⇒ 若"包内端到端事实"走 `ledger()`，
`--release` 可以在**这三条一次都没真跑**的情况下打 PASS —— 那是假绿。所以 release 档必须走 `prereq`。

### 1.3 子进程统一入口 `run(cmd, env, timeout=600)`（112-146）

| 行为 | 细节 |
|---|---|
| CWD | **恒为仓库根** `ROOT`（137）—— 脚本里若有依赖 CWD 的相对路径，等价于依赖"从仓库根跑" |
| 编码 | 子进程强制 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8` |
| TEMP | **每步独占**一个 `%TEMP%\rctmp_<pid>_<ms>`（122-128）—— 隔离 `--smoke` 的 `%TEMP%\xrkit_smoke_*` 互撞 |
| 残留进程 | 每次起子进程前 `taskkill /F /T /IM xrkit_app.exe`（130-133） |
| 超时 | 返回码 **124** + `[超时 Ns]`（144-146）—— 调用方必须把它当失败判（不是 SKIP） |
| 输出 | stdout+stderr 合并、UTF-8 解码（replace） |

★ 顶部还**自己**重编码 stdout（62-66）：修前只给子进程设 UTF-8，脚本自己打印 `✓/✗` 可能
`UnicodeEncodeError` ⇒ 退 1 且**没有 RESULT 行**（"红但不说哪一步"）。

### 1.4 汇总层（7328-7411）

```
for name, fn in STEPS:            ← 顺序即依赖（见 ② 的分组）
    if --only 且不匹配: continue   ← 不执行；收尾按"未执行"记账
    before = FAILURES
    fn(release)
    if 该步首次判红 且 name ∈ FLAKY_RETRY: 复跑一次；绿 ⇒ 撤销首次计数并登记"飘"
收尾:
    missing = STEPS - ran ⇒ UNCOVERED（"--only 过滤掉"与"一个都没匹配上"分开说）
    release 且 UNCOVERED ⇒ FAILURES += 1
    版本快照恢复 + 断言（_restore_and_assert_version_json，**在打印 RESULT 之前**）
    flaky_seen ⇒ ledger（可见、不阻断）
    FAILURES ? "RESULT: FAIL（N 处失败）" : "RESULT: PASS"
```

**★ 三类"未覆盖"来源（都进 `UNCOVERED`）**
1. `prereq()` —— 外部前提缺件；
2. `--only` 过滤掉的步骤（7305-7311 的修复：修前直接 `continue`，`--release --only winres` 能一键变绿）；
3. `package_fact()` 在 release 档的前提缺失。

**★ 一个"允许复跑"的白名单**（7326）：`FLAKY_RETRY = {golden-sqfs-pack-real, pkg-platform, release-criterion}`
—— 只这三个，只复跑一次，且**必须留痕**（`≈ … 首次红、复跑绿 ⇒ 登记为"飘"`）。
★ 复跑绿不算"干净"：收尾会把它记进 `LEDGERS`（P17-135：原来 `flaky_seen` 只 append 没人读）。

### 1.5 已知的"版本三件套"耦合（P17-130/133，7302 / 7332-7336 / 7382-7394）
- 开场 `_snapshot_version_json()`；
- **每个步骤前后**算一次 `version.json` 的 sha（`_vw_mark`）⇒ 收尾能点名"哪个步骤改过它"；
- 收尾 `_restore_and_assert_version_json()`：逐字节恢复三件 + 断言；
- ★ 实测结论：被点名的永远是 `shell-smoke`（它跑打包脚本，脚本写 version.json），
  而 `--only shell-smoke` 单跑不复现 ⇒ **写入依赖前面步骤留下的状态**；收敛条件是"那段在门禁状态下不写"。

### 3.1 三处"必须先有产物"的硬依赖（顺序不能换）
1. `build` → 后面所有读 `xrkit_cli.exe` 的步骤；
2. `shell-smoke` → 编出 `xrkit_app.exe`（`winres` 要读它的资源字节）；
3. 打包（`run_ci` 之外）→ `pkg-platform` / `package-pages` / `release-criterion` / `version-identity`。

### 3.2 本批**改了一处**（与用户口径对齐）
`step_shell_smoke` 原来只看 `rc==0 && "SHELL-SMOKE ok" in out` —— 而自检的第三态
`not_covered=K` 现在会出现在收尾行里，**K>0 时 failed 仍可能是 0** ⇒ "没验"会被读成"验过了"。
现在：解析 `not_covered=(\d+)`，K>0 时走 `prereq`（release 档 FAIL，其它档 SKIP + 未覆盖清单）。
★ 只加"可见 + 记账"，**没有改任何判据内容**。

## 四、隐藏耦合（本批完成，盯的四个点）

### 4.1 版本三件套：谁读、谁写、谁恢复（`run_ci.py:7164-7290`）

| 角色 | 位置 | 行为 |
|---|---|---|
| **快照** | `_snapshot_version_json()`（7240） | 门禁**开场**逐字节快照**三件**：`version.json` / `include/xrkit/core/version.h` / `assets/xrkit_winres.rc`（`_VERSION_IDENTITY` 7233） |
| **逐步骤监视** | `_vw_hash()` + `_vw_mark(name)`（7178/7202） | 每步**之后**算一次 `version.json` 的 sha16；变了就打印 `!! 步骤 X 改了 version.json（prev → now）`，并**带上那一刻还活着的进程**（`xrkit_*`/`ffmpeg`/`ffprobe`/`windeployqt`/`cl`/`link`） |
| **恢复 + 记账** | `_restore_and_assert_version_json()`（7248） | 收尾：三件**逐字节写回**；改过的文件逐个点名；然后 **`ledger(...)`**（不是 fail） |
| **谁写** | 只有 `xrkit_cli --build-package`（见 §5） | 门禁里会触发它的步骤：`release-criterion`（真跑 `package.ps1 -Dev:$false`） |
| **恢复失败谁报红** | 恢复本身**不判红**（按 P17-130：常红的判据等于没判据） | 恢复失败会在下一次 `version-identity` / `VERSION-IDENTITY` 步骤被抓到（它读三件 + 包内 exe）；另外 `_vw_mark` 的点名是**永久可见**的 |

★ **崩溃时是否一定恢复**：**不一定** —— `_restore...` 在 `main()` 收尾，若脚本被 `Ctrl-C`/异常打断则跳过。
但那时**三件已脏**，下一次门禁 `version-identity` 会红（它比 tree/version.h/.rc/包内 exe），所以**不会静默**。

### 4.2 `gen-drift` 会不会改生成文件（`step_generated_drift` 6662-6700）

- 调 `tests/check_generated_drift.py`：**真跑一次生成器**（只用本地锁、不联网）重写 `third_party/SOURCES.md`，
  与库里那份**逐字节比**；**无论结果都恢复工作区**（脚本内 `finally`）；
- 幂等：生成器重跑应得同一字节（这正是它判的）；`rc=2`（缺生成器/锁/生成物）⇒ **FAIL**（仓库自带件，不许 SKIP）。

## 九、Q2 落地：包内 exe 的 `exe_sha256=`（2026-10-23，**未跑整档**）

### 9.1 语义（按用户口径）

| 环节 | 谁做 | 细节 |
|---|---|---|
| 算 & 写字段 | **`xrkit_cli --build-package`（唯一写入者）** | `build.ps1` 成功后先算 `build/msvc-shell/src/shell/xrkit_app.exe` 的 sha256 并打印 `BUILDPKG exe-sha256=…`；把它作为 `-ExeSha256` 传给 `package.ps1`；包**落到最终目录之后**，算**包内那份** exe 的哈希（必须等于之前那份），原子写进 `version.txt` 的 `exe_sha256=`，再**读回比对** |
| 核对（不写） | `scripts/package.ps1` | 新增 `-ExeSha256`；用 `xrkit_cli --sha256 <舞台 exe>` 现算，与期望值逐字比；**不一致或没传 ⇒ throw（包不落地）** |
| 独立第三只眼 | `tests/check_version_identity.py` ④ | 用 Python `hashlib` 再算一遍包内 exe，与 `version.txt` 的 `exe_sha256=` 逐字比；顺带断言 `version=`/`index=` 与 `current` 一致 |
| 老包（无该字段） | 同上 | **退 3（NOT-COVERED）**；门禁 `release` 档 `prereq` ⇒ **FAIL**，其它档记 SKIP + 未覆盖清单（**不冒充通过**） |

### 9.2 新增的唯一哈希实现（core，无 Qt）

`include/xrkit/core/sha256.h` + `src/core/sha256.cpp`；CLI 新动作 `--sha256 <文件>`（输出 `SHA256 <hex> <path>`）。
这样打包链（PS）、CLI、判据（Python）**共用同一个语义**，且 C++ 实现与 Python `hashlib` **跨语言对拍通过**：

```
version.json                              py=8a94c36b140e66fc cpp=8a94c36b140e66fc OK
build/msvc-shell/src/shell/xrkit_app.exe  py=cf266431f112c898 cpp=cf266431f112c898 OK
dist/2.0.0/BETA/1/version.txt             py=4ab62f358b458607 cpp=4ab62f358b458607 OK
```

### 9.3 实测（未跑整档，只跑定向）

| 场景 | 结果 |
|---|---|
| `--sha256` 对三个文件 vs Python `hashlib` | **逐字相同** |
| `check_version_identity.py`（current=BETA/1，老包） | `NOT-COVERED（包缺 exe_sha256=）`，**rc=3** |
| `run_ci.py --fast --only version-identity` | **PASS** + `SKIP 包内 exe 的 sha256 不变量（…）`（记入未覆盖） |
| `run_ci.py --release --only version-identity` | **FAIL**（`prereq` 零容忍）—— 老包不具备新不变量，**不是回归** |
| 反例①（把临时副本的 `exe_sha256=` 写成全 0） | `✗ ④ 包内 exe 现算的 sha256 == version.txt 的 exe_sha256=`，**rc=1** |
| 反例②（自证：把包内 exe 改一个字节） | `✓ 自证：… 必须与 exe_sha256= 不同` |

### 9.4 与老包的关系（预期行为，写清免得误判）

- `BETA.1` / `BETA.258` **都没有** `exe_sha256=` ⇒ 在 `current` 指向它们时：
  `--fast` 的 `version-identity` = **NOT_COVERED**（记未覆盖），`--release` = **FAIL**；
- **重打一个新包（BETA.2）后**，新包自带该字段 ⇒ 两条路径都回到正常判定；
- 收敛条件：`current` 指向"带 `exe_sha256=` 的包"，这一条就再也不出现。

### 9.5 已知残余（本轮不做）

- **进程被强杀**时 `--build-package` 的回滚不会执行（三件套停在失败那一格）——下次可加"启动时检测三件套不自洽 ⇒ 提示/安全模式"的守卫；
- `package.ps1` 的 `-ExeSha256` 目前靠 CLI 传；手工跑 `package.ps1` 会被**明确拒绝**（throw），这是有意的。
