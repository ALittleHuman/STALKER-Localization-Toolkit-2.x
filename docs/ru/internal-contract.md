# Внутренний контракт (для сопровождающих)

Жёсткие правила для тех, кто меняет код; пользовательская документация — в `user-manual.md` / `plugin-development.md`.

> Плагины поддерживаются только как Python-файлы/каталоги; `PLUGIN_API = 2` — версия контракта Python API (совместим с API 1), не бинарный ABI.

## 1. Ключи sink плагинов

- `row_kind` в `XmlCompareResult` не входит в структуру, только подсказка рендерингу;
- неизвестные ключи sink обязаны попадать в `unhandled_keys` по одному; молча терять нельзя;
- `ids_a`/`ids_b` считаются по фактически переданным плагином ID, нельзя брать `id_text_*` из текстового режима (путь плагина всегда пуст).

## 2. Семантика фильтра

- фильтр фасада смотрит `item->text(column)` (видимую пользователю ячейку), скрытые столбцы не учитываются;
- встроенные страницы хранят попадания поддерева в `matched_paths_`; от него зависит видимость родителя.

## 3. Загрузка и отмена (одна реализация)

Единый вход: `core::DownloadManager`.

- обновление хоста: `HostUpdate::downloadAppUpdate` → Manager;
- синхронный плагин: `api.host.http_download` → Manager;
- асинхронный плагин: `api.host.http_download_async` → Manager;
- низкий уровень только `core::http_download` / `http_download_range`;
- части: `<target>.part.N` + `<target>.segments`;
- отмена: `DownloadManager::cancel`; кнопка хоста/плагина `http_cancel` в итоге вызывает её;
- выгрузка плагина: `cancel_owner(owner)`;
- завершённый job хранится 10 минут для опроса, затем join/очистка.

**Запрещено** добавлять второй цикл загрузки, второй конечный автомат `.part` или загрузку с отдельным флагом отмены.

## 4. Состояние обновления

- `pending.json` отвечает только за установку (версия/zip/ready);
- точки докачки принадлежат Manager, `pending.json` больше не используется для этого;
- атомарная ротация `.bak/.tmp`; при запуске читаются current/bak, при повреждении — откат;
- в Release с несколькими zip asset выбирается по build и к нему подбирается digest;
- старые каталоги пакетов не удаляются автоматически.

## 5. Модель версий C

- единственный источник порядка — `version.json.build_counter`, +1 на сборку;
- стабильная `x.y.z`; тестовая `x.y.z.<build>`;
- `kChannel` содержит только имя канала (BETA/RC/ALPHA), `kBuildNumber` — глобальный build;
- dist: `dist\x.y.z\<канал>\<номер_канала>`;
- в `version.txt` пакета пишутся и `index`, и `build`;
- тестовые сравниваются по build; стабильная выше тестовой той же версии.

## 6. smoke и приложение

- `xrkit_app.exe` не содержит `smoke.cpp` / `--smoke`;
- `xrkit_smoke.exe` — отдельная цель со своими ресурсами версии/manifest;
- в релизный пакет smoke не входит; `package.ps1` временно копирует его для проверки и удаляет;
- проверки/скрипты используют `xrkit_smoke.exe`; не добавляйте smoke-ветку обратно в app.

## 7. Обход и чтение файлов

- рекурсивный обход — только `fs::collect_tree`, не добавляйте `recursive_directory_iterator`;
- чтение файла целиком — только `core::read_file_capped`, по умолчанию 512 MB, превышение — явная ошибка;
- сознательно не подключено: чтение DB целиком (untrusted_limits), обратное чтение внутренних продуктов, atomic_write backup, чтение журналов.

## 8. Сжатие SquashFS

- чтение: xz / gzip / lzo / lz4 / zstd;
- запись: только xz (по умолчанию) + gzip; возможности чтения и записи **несимметричны**;
- компрессоры записи, которых нет: lzo, lz4, zstd;
  - lzo: в minilzo нет lzo1x_999;
  - lz4: нужен 8-байтовый блок options (семантика COMPRESSOR_OPTIONS);
- по умолчанию запись — xz; gzip для записи уже реализован, это не обещание.

## 9. sniff текста

- решение = доказательств >= 2 и |score| >= 0.15 (те же константы, что в `sniff.cpp`).

## 10. Оставленные интерфейсы без вызовов

| Символ | Причина |
|---|---|
| `plugin::set_host_facade()` | Точка внедрения фасада хоста на будущее |
| `core::case_fold_ascii()` | Семантика ASCII и Unicode fold различается, оставлено |
| `Registry::register_format()` | Подключено к Python `api.register_format`, не мёртвый код |

Удалено и не добавлять: CLI `--app-update`, перечисления трёх имён методов C ABI, `Registry::has_command()`.
