# 2.0.0 文本模块规格（M1-6，第一版：解码层 + 文本提取）

> **判据（用户口径，不许降级）**：**产物逐字节一致**；真机样本；红着绝不提交。
> 落地方式：同一份输入，我们的产物与 1.x 的同名实现**逐字节相同**。

## 0. 1.x 有**两条不同的链**（先分清，别混）

| 链 | 1.x 实现 | 谁在用 | 本轮 |
|---|---|---|---|
| **A. 六编码链**（确定性，无统计） | `toolkit_textio.read_text_file:305-316`：`utf-8-sig → utf-8 → gb18030 → windows-1251 → windows-1252 → latin-1`，前五种 strict，**末位 latin-1 兜底** | **文本提取页**（`_parse_cfgxml` / `_parse_script` / `_parse_ltx` 全走它） | **本轮做** |
| **B. 判定链**（六步，含统计探测） | `toolkit_textio.sniff_encoding:171-244` + `decode_bytes:247-290` | 编码转换页（`convert_app`） | 下一轮（见 §5 记账） |

两条链**顺序与判据都不一样**：A 是"谁能严格解开就用谁"，B 是"BOM → 多字节 → 手动 → 声明 → 统计 → 默认"。
把它们当一个东西是实现错误。

## 1. 实测（2026-09-24，真语料 300 个文件，`_2x_ref/sniff_probe.py`）

判定链（B）各步胜出频次：

| 步 | 含义 | 次数 |
|---|---|---|
| 1 | BOM | 16 |
| 2 | 多字节 UTF-8 | 4 |
| 4 | XML 声明（且被字节证实） | 78 |
| 5 | 统计探测（chardet） | 146 |
| 6 | 默认 windows-1251 | 56 |

**统计步"决定性"的样本 = 0 个**：146 次里 144 次 chardet 给的是 `ascii`（纯 ASCII 文件在任何 ASCII 兼容编码下解出的文本完全相同），
2 次给 `utf-7`（`decode_bytes` 随后必然回落 windows-1251）。也就是说：**在真语料上，不移植 chardet 不会改变任何一个文件的解码结果**，
只会改变"报出来的编码名"。这条实测是 §5 记账的依据。

## 2. A 链（本轮做）的规则清单

| # | 规则 | 证据 |
|---|---|---|
| 1 | 顺序固定 `utf-8-sig → utf-8 → gb18030 → windows-1251 → windows-1252 → latin-1` | `read_text_file:305-316` |
| 2 | 前五种**严格**解码；最后一种 latin-1 用 `errors="ignore"`（latin-1 永不失败，实际等价于不忽略） | 同上 |
| 3 | `utf-8-sig` 命中时**返回的编码名就是 `utf-8-sig`**，且解码会**吃掉 BOM** ⇒ 写回时 Python 又会**加上 BOM**。UTF-8 源文件经提取后产物带 BOM，这是 1.x 的真实行为，必须复刻 | `codecs` 语义 + `_generate_output_file:218-226` |
| 4 | 严格解码失败的字节必须有**未定义哨兵**（cp1251 的 0x98、cp1252 的 0x81/0x8D/0x8F/0x90/0x9D）—— 否则会错误地"解成功"，整条链的落点就变了 | 本机 `python -c` 实测 |
| 5 | gb18030：单字节 0x00-0x7F 直通、0x80→U+20AC、双字节表、四字节线性段 | Python `gb18030` codec（表由生成器从 codec 导出） |

复刻的产物：`include/xrkit/engine/text/encoding.h` + `src/engine/text/encoding.cpp`；
表由 `tools/gen_encoding_tables.py` 从 **Python 的同名 codec** 生成（与 `fs/cp1251_tables.inc` 同一姿势），
`--check` 模式做"表与 codec 一致"的锁。

## 3. 文本提取的规则清单（同一轮做）

三个分支（1.x `apps/text_extract_app.py`）：

| 分支 | 输入 | 候选来源 | 替换形态 |
|---|---|---|---|
| cfgxml | `*.xml` | `CFG_TAG_PTN`（text/bio/title/name 标签内容）+ `CFG_ATTR_PTN`（hint/name 属性，只取 `len>2` 的引号内内容） | 直接换成 ID |
| script | `*.script` | 逐行引号状态机（`_get_script_texts`），带引号字面量 | 整段带引号字面量 → `game.translate_string("<id>")` |
| ltx | `*.ltx` | `inv_name*` / `description` / `title` / `descr`（`{...}` 原样标记剔除、逗号拆条） | 用 `_ltx_source_literal` 定位整段字面量（含引号）再换 |

必须复刻的纪律（都是 1.x 注释里写明的血账）：

1. **候选遍历一律排序**（`sorted(cands)`）—— set 的迭代顺序随进程哈希随机化，不排序会让同一份源两次运行得到不同 ID。
2. ID 前缀：`sgtat_{prefix}_{gp|sc}_{ts}`；类型段是**显式缩写映射**（不是 `ftype[:2]`）。
3. 处理顺序固定 gameplay → scripts；只处理选中的那一类（目录名必须是 gameplay/scripts，否则拒绝）。
4. 输出：改写后的源文件写进 `输出/{gameplay|scripts}/`；文本 XML 固定 `utf-8`、
   `\t` 缩进、正文按 1000 字符切行、某一类没提到文本就**不产出**该 XML。
5. 跳过：`translated_*` / `text` 路径段、本工具自己的产物 `*_(gameplay|scripts)_texts.xml`。
6. 正则用 **PCRE2**（`std::regex` 不支持 lookbehind）：`PCRE2_UTF | PCRE2_UCP`，
   与 Python `re` 的 Unicode `\s`/`\S` 语义对齐。

### 3.1 ★ 两个分支的**写回编码不一样**（实测抓出来的，别"统一"）

| 分支 | 1.x 调用 | 写回编码 |
|---|---|---|
| gameplay | `_generate_output_file(out, text, **encoding=enc**)` | 用**检测到的**编码（utf-8-sig 会补 BOM、cp1251 严格编码） |
| scripts / ltx | `_generate_output_file(out, text)` —— **没传 encoding** | 走默认 **utf-8** |

后果：scripts 侧即使源是 cp1251，产物也是 UTF-8（字节数与源不同）；gameplay 侧则"原样编码"写回。
我们第一版把两边都写成检测编码 → 合成 scripts 夹具 5 个文件全红（205 vs 178 字节）。
**只看条数、只看文本 XML 永远发现不了**——那些都是对的。

### 3.2 另一个字节级细节：Python 文本模式**写**

`_generate_output_file` 与 `_generate_text_xml` 都用文本模式写，Windows 上会把 `\n` 翻成 `\r\n`。
而读取时文本模式又会把 `\r\n` 归一成 `\n`。所以"CRLF 源 → CRLF 产物、LF 源 → CRLF 产物"，
两个分支都如此。漏了这一步，凡是 LF 的源文件都会差一截字节。

### 5.1 已拍板（用户 2026-09-24）：**不复刻** 1.x 的 cp1250 误判

实测（`_2x_ref/gap_detail.py`）：`Games\Golden Sphere\gamedata\scripts` 的 **468 个真文件里
68 个（14.5%）** 被 1.x 的判定链判成 **cp1250**（chardet 失误，而 `_CYRILLIC_ALTS` 名单只挡了
MacCyrillic / ISO-8859-5 / KOI8-R 等，**漏了 cp1250/cp1252**）→ 这些文件的西里尔正文会被解成
Latin-2 重音字母（乱码）；而这些文件自己在 Lua 注释里写着 `coding: windows-1251-dos`。

**用户拍板（原话）："解包最终是要和原版 cv 对齐的。"** ⇒ 取选项 ①：2.0 给正确俄文，
**与 1.x 在这 68 个文件上有意不同**；差异已在门禁 [15] 的差异台账里冻结
（类别 `misdetect-single-byte`），文档与运行日志照此说明。

> 由此确立的判据层级：**最终参照＝原版工具/游戏**（原版 converter.exe、引擎行为），
> 1.x 只是"行为代理"；**1.x 与原版冲突时以原版为准**，并把差异记进台账。


### 5.3 utf-16 / utf-32 家族的**有损**编解码：判据已定，实现待补（2026-09-25）

现状：`decode_lossy` 对 utf-16/32 家族**如实报错**（不假装支持），转换页下拉也不列它们
（"只列做过逐字节对拍的编码"）。本节把**判据**先钉死，实现时照这张表写、照它验。

判据＝**Python `errors="replace"`**，真值表由 `tests/probe_utf_lossy.py` 生成（直接跑它即可
复现；本表是它 2026-09-25 的输出蒸馏）。**实测语义**（decode，`native = LE`）：

1. **BOM 只在"带 BOM 的编解码器"里被吃掉**：`utf-16` 首两字节 `FF FE` ⇒ 吃 BOM 走 LE；
   `FE FF` ⇒ 吃 BOM 走 BE；**没有 BOM 就用本机序（LE）且不吃任何字节**。
   `utf-16-le/-be` **永不**吃 BOM（BOM 会作为 U+FEFF/U+FFFE 出现在正文里）。
   utf-32 同理：`FF FE 00 00` ⇒ LE、`00 00 FE FF` ⇒ BE，无 BOM 则本机序。
2. **utf-16 单位是 2 字节**：尾部**奇数字节** ⇒ 恰好 **1 个 U+FFFD**（不看剩下几字节）。
3. **代理对**：高位 `D800..DBFF` 后面跟着低位 `DC00..DFFF` ⇒ 合成一个码位；
   否则（后面不是低位／到末尾／单独的低位）⇒ **每个问题单位各 1 个 U+FFFD**。
4. **utf-32 单位是 4 字节**：尾部 1~3 字节 ⇒ **恰好 1 个 U+FFFD**（不是按字节数给几个）。
5. **utf-32 的非法码位**（`> 0x10FFFF`、代理区 `D800..DFFF`）⇒ 1 个 U+FFFD。
6. **空输入 ⇒ 空输出**（含"只有 BOM"：BOM 被吃 ⇒ 空）。

encode（同样是 `errors="replace"`）：

7. `utf-16` / `utf-32` **写出 BOM 且用 LE**（`FF FE` / `FF FE 00 00`）；`-le/-be` 不写 BOM。
8. **表示不了的码位（单独代理）⇒ `?`（0x3F）**，按该编解码器的字节序写（utf-16-le: `3f 00`，
   utf-16-be: `00 3f`；utf-32 对应 4 字节）。
9. 正常码位：BMP 按单位直写；astral（如 U+1F600）utf-16 走代理对、utf-32 按 4 字节。

实现清单（照做即可收口）：`encoding.cpp` 加 utf-16/32 的有损解码与编码（可与严格路径共用
一个"单位扫描"内核）；`lossy_encodings()` 六项加进下拉；`tests/golden_lossy_codec.py` 加
`cases_by_codec` 六项（该脚本的期望值**现算**自 Python，所以加用例即完成对拍）。
