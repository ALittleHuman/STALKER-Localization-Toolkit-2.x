## A. 引擎行为（不定就会走歪）

**A1. 大端镜像 `sqsh` 支持到什么程度？**
现状：`sqfs_check` 认 `sqsh` 是 `sqfs`（`stalker_fs.py:996-1006`），但元数据直读入口硬判 `b"hsqs"`（`1061`）→ 大端镜像**列表可用、大小全 0**。
- 建议：**2.0 补全**（大小端只是字节序，补它几乎零成本，且能消掉一类"大小显示 0"的现场疑问）。

**A2. 压缩算法覆盖到哪？**
现状：`_sqfs_decompress` 支持 1=gzip / 4=xz / 5=lz4 / 6=zstd；**2=旧 lzma、3=lzo 直接抛异常**（`1104-1116`）。
- 建议：**补齐 lzo 与旧 lzma**（lzo 有稳定开源实现；补上之后"NLC 现场 lzo 镜像取不到大小"这个 1.1.0 遗留缺口也就消了）。

**A3. SquashFS 封包怎么写？（最重的一条）**
现状：1.x **不自写 writer**，封包＝调外部 `tar2sqfs.exe -q`，stdin 喂 tar（`1445-1483`），默认压缩器 = **xz**（已实测 `--help` 写着 `xz (default)`）。
- 选项 ①：2.0 自写 SquashFS writer（完全进程内，不受杀软影响）
- 选项 ②：继续调 `tar2sqfs.exe`
- 选项 ③：先①后②兜底
- **建议：①自写**。理由是 1.x 的血账——`sqfs2tar.exe` 被 360 **按文件哈希拦**（`Access is denied`，复制改名也没用，`stalker_fs.py:1047`），外部 exe 在这台机器上是不可控依赖；而且自写才能控块大小/压缩器。

**A4. 压缩器默认值**（A3 若选自写）
- 建议：**默认 xz 块**，与 1.x 产物同族（引擎兼容性最稳），并在 UI 上给 gzip/lz4/zstd 选项。

**A5. 整包读入内存改成流式读取**
现状：1.x `load_db()` 把整个镜像读进 `bytes`（`stalker_fs.py:759-764`），8.3 GB 镜像直接爆内存（实测缓冲 8.49 GB → `MemoryError`，ARCHITECTURE §11.15）。
- 建议：**2.0 必须改**（mmap + 按 `offset/size_comp` 预读），并把「提取」的签名从"整包 bytes"换成"句柄+条目"。

**A6. 「散装文件作为最后一层并入树」要不要在 2.0 做？**
现状：1.x **未实现**（用户口径已定「后者为准 + 散装最后覆盖」，但代码只做了归档层合并）。
- 建议：**2.0 做**（这是用户已拍板的引擎口径，2.0 正好一并落地）；进入方式＝拖目录进「数据包列表」新增「散装层」条目。

**A7. 整镜像解包路径安全**
现状：1.x 选中的条目走 `safe_out_path` 六条校验（`1313-1341`）；**整镜像 `--unpack-path` 分支的路径安全由外部工具负责，仓库未验证**（ARCHITECTURE §11.15「只报告未改」）。
- 建议：2.0 自实现时**两条路都必须过同一套路径校验**，并把 1.x 那条缺口一并关掉。

## B. 插件 ABI（你说的 DLL 方案，具体形态要定）

**B1. ABI 形态**
- 选项 ①：纯 **C ABI** + 版本化结构体（`extern "C"` 导出 `stk_plugin_init(const stk_host_api*, uint32_t abi_version)`）
- 选项 ②：COM 式 vtable
- 选项 ③：C++ 抽象基类（简单，但要求插件与主程序同编译器/同运行库，脆弱）
- **建议：①纯 C ABI + 版本化结构体**（编译器无关、崩溃面小；闭源插件只暴露函数表）。

**B2. 插件能力面保留多少？**
现状：1.x 有 11 个注册点（解密器 / 格式 / 命令 / 菜单项 / 下拉条目 / 选项 / 面板 / 工具 / 比较模式…），其中只有 3 处与 UI 强耦合。
- 建议：**保留解密器 + 格式 + 命令 + 菜单项 + 下拉条目 + 选项 + 比较模式**（都是"宿主渲染的纯数据 + 回调"）；面板/工具（要插件自己造控件）**砍掉**——插件生态已经不重要，保留它要背整套 UI 契约。

**B3. 1.x 的三条 Python 插件怎么办？**
`plugins/engine_utf8_patch.py`（补丁插件，实验性）与闭源 `nlc_sqfs.py`（NLC 解密）。
- 建议：**都移植成 C++ 内置模块或 DLL 插件**；闭源的那份继续**不随包发布**（1.x 已有这条规矩）。

## C. 行为与实现手段

**C1. 六页形态是否原样保留？**（文件系统 / 编码转换 / 文本提取 / XML 校对 / 视频转换 / 汉化包生成）
- 建议：**原样保留**（含 XML 校对的两种模式），2.0 只换实现不换功能面；新功能另开版本。

**C2. 文本提取的正则要换引擎**
现状：1.x 的正则用了 **lookahead/lookbehind**（`text_extract_app.py:59-64`），而 C++ `std::regex` 的 ECMAScript 方言**不支持 lookbehind**。
- 选项 ①：引入 **PCRE2**（成熟、语法最接近 Python `re`）
- 选项 ②：改写正则绕开 lookbehind（逐字符状态机已在 1.x 用过，可行但要重验）
- **建议：①引入 PCRE2**（改写正则是返工高发区，不值得为一处语法让整页逻辑变形）。

**C3. 字库产物要不要与 1.x 逐字节一致？**
现状：1.x 用 Pillow 渲染 + `LANCZOS` 重采样（`font_pack.py:834-835`），其精确采样相位/边界难以在 C++ 复刻。
- 选项 ①：追求逐字节一致（要复刻 Pillow 内部实现，成本极高）
- 选项 ②：**视觉等价 + 判据量化**（墨迹高 ≤ cell−4、墨迹宽 ≤ min(推进宽, cell)、框宽 ≤ cell、逐槽位与参照包偏差 ≤1px，这些 1.x 已有实测基线）
- **建议：②**。理由：1.x 自己就是用这套"量得出来的判据"定标的（`667-717`），逐字节一致换个字体版本就会破功。
