## 零、先答「C ABI 留着干什么」——审计结果：**它不是 ABI，是内部桥梁**

| 检查 | 命令/位置 | 结果 |
|---|---|---|
| 是否**导出** | `dumpbin /exports xrkit_app.exe`、`xrkit_cli.exe`、`xrkit_build_gui.exe` | **导出符号 0 个**（三个 exe 全 0）；我们**不产出任何自己的 dll** |
| 是否有导出宏 | `git grep 'dllexport\|STK_API'` | **无** |
| 声明形态 | `include/xrkit/engine/plugin/facade_api.h` | `extern "C" { ... }` + 函数指针表（`stk_ui` 16 方法），**只有 C 链接、没有导出** |
| 消费者 | `git grep stk_ui` / `plugin_ui` | 全部在**仓内**：`src/shell/hub.cpp`、`plugin_ui.cpp`、`widget_facade_qt.cpp`、`smoke.cpp`；`src/engine/plugin/py_host.cpp`（Python 绑定共用这张表）；`tests/run_ci.py`（`ui-facade` 步核"16 方法都有实现"）；docs/README |
| 外部第三方能否链接 | 不能（不导出） | — |

⇒ **身份判定：宿主内部契约（internal bridge），不是公开 ABI。** 与你说的"第一种"一致：
没有外部消费者，所以不存在兼容承诺；但它是**活代码**（外壳实现、Python 绑定消费），**不属于死代码，本次不删**。

### 建议（不在这批做，单独立项）

1. **去 ABI 化措辞**：README/设计口径里"控件门面契约（`stk_ui` 16 方法）"改成"**宿主内部控件工厂表**"，
   并明确"**不承诺二进制兼容**"；
2. **加一条门禁**（很便宜）：公开头文件（`include/**`）里**不许**出现 `__declspec(dllexport)` /
   `STK_API` / `__declspec(dllimport)` 之类导出宏 —— 防"有人把它变成真 ABI 而不自知"；
3. `ui-facade` 那条 16 方法检查**保留**（它现在验的是"表形状 + 都有实现"，属**契约漂移**检查，
   不是"为旧 ABI 续命"）；但注释里"与 1.x 对齐"要改成"表形状固定（参数名沿用 1.x 只为读得懂）"；
4. 若将来确认**永不做原生插件**：把 `facade_api.h` 从 `include/` 移到 `src/shell/`（降为私有头），
   这是"降内部"的最小动作 —— 但**不是这批**。
