## A. `sniff.h`（116 行）—— 判定链与"置信度系统"

### 1. 六步链**顺序不可改**（第 4-6 行）
`1 BOM（物理事实）→ 2 多字节（能按 UTF-8 解且含 ≥0x80）→ 3 手动指定 → 4 XML 声明（**必须被字节证实**）
→ 5 统计探测（"鲁棒"）→ 6 默认 windows-1251`

### 2. ★★ 用户四段原话（第 8-17 行，逐字遵守）
- 「**单/多字节识别 > 手动 > 声明 > 鲁棒**」；
- 「鲁棒和声明实际上地位差不多……**我个人是非常不建议自动识别的**」；
- 「**字节判断和手动设置是死板的**……**后面的两个才是不确定因素**，也就是置信度系统」；
- 「**声明的优先级仍然比鲁棒稍微高一点**……**我仍然选择保留 auto 选项**」。

⇒ 落地：第 1/2/3 步是**锁**（语义一字不动，含 `auto` 仍保留）；第 4/5 步合并成**一个置信度系统**：
统计有决定性且与声明不一致 ⇒ **否决声明**（`override_decl` 必须可见）；
统计无决定性 ⇒ 声明照旧；两者都没有 ⇒ 第 6 步默认，**纯猜**，必须 `low_confidence`。

### 3. ★★ 有意与 1.x 不同（第 26-29 行）
1.x 第 4 步只要 `bytes_fit_encoding` 通过就 `return`，而单字节编码下那道闸门**几乎是空的**
（cp1251 只有 0x98 一个未定义字节）⇒ **谎报 `windows-1251` 的 cp1252 文件 100% 静默走错**。
2.0 改成"声明必须被字节证实 + 与统计一起裁决"。

⇒ 这是"**判据（闸门）在输入空间上几乎恒真 ⇒ 等于没有**"的实例。
  我们判"页就绪"的 `layout()->count() > 0` 就属于这类**几乎恒真**的判据 —— 该警惕。

### 4. 9.7 的修正（第 64-71 行）：标签不许复算
1.x 的"定案步骤"标签是 `convert_app` **复算**的（只查有没有 XML 声明、**不校验字节证实**）
⇒ 标签能与判定本身矛盾（实测：字节是 UTF-8、声明写 windows-1251 的文件被标成 `声明(utf-8)`）。
2.0 只发**步号**，标签由步号唯一决定，页面不许自己拼。

⇒ **"标签/文案只有一个来源"是我们判据 note 该守的纪律**：note 里的原因也该由产品给，
  判据只负责搬运，不要自己拼一套解释（否则两边会矛盾）。

### 5. `used_mismatch`（第 95-97 行）
实测量到过 `enc=windows-1251` 但 `used=windows-1252` 的**静默分叉** ⇒ 必须报出来。

### 6. `bom_encoding`（第 100-102 行）：UTF-8 的 BOM 归一为 `"utf-8"`
1.x 口径：返回 `utf-8-sig` 会让"判定出的编码"与"实际用的编码"对不上。

## B. `batch.h`（217 行）—— 批处理层

### 1. 为什么不放在页面里（第 13-19 行）
① 全是纯文件 IO、没有一行需要 Qt；② 放这里才能被 **CLI 自检逐条驱动**（页面那份只能靠离屏 GUI 自检，
代价高得多）；③ 用户口径"GUI 的功能 CLI 必须全有" ⇒ 批处理口径**只有一份实现**。

★ 递归遍历**不新造**：转调 `engine::fs::collect_tree()`（自带 `WalkReport` 台账）
—— 「同类东西只维护一套组件」，不许出现第 5 份 `recursive_directory_iterator`。

### 2. ★ `glob_match` / `is_excluded`（第 31-46 行）：**逐条复刻，不"统一成一套"**
1.x 三条判据：① `fnmatch(basename, pattern)`；② `fnmatch(rel_path, pattern)`；
③ `pattern.replace('*','') in rel_path`。
★ `fnmatch` 在 Windows 走 `normcase`（**小写化**）⇒ ①②**大小写不敏感**；③ 是 Python `in`
（**大小写敏感**）。**这里逐条复刻**，因为统一了就会与 1.x 分叉。
★ 分隔符：1.x 的 `rel_path` 是 `\`，我们内部是 `/` ⇒ 三条都**同时喂两种写法**。

⇒ 两条可直接搬的教训：
  ① **对拍口径不许"顺手优化成一套"**（哪怕看起来更合理）；
  ② **输入归一要比对"用户会怎么写"，不是"我们内部怎么写"**。

### 3. 零静默（第 21-22、57-69、194-201 行）
所有"跳过/排除/读不到"都**计数 + 逐条留痕**；`exit_code` 在"有失败/有遍历错误"时非 0
（**部分失败也是失败**）。
`CollectReport` 的字段就是一份"为什么没选中"的分类账：
`skipped_ext / skipped_excluded / skipped_backup / skipped_depth` + `excluded[]` + `errors[]`。

### 4. ★★ 退出码语义表（第 202-211 行）—— 可直接抄
```
0 = 全部成功
1 = 有失败 / 有遍历错误（部分失败也是失败）
2 = 输入不可用
3 = **需要用户确认**（needs_confirm；不猜、不替用户选）
```
且 `needs_confirm` 有 `confirm_path / confirm_question / confirm_diagnostics` 三个具名字段
（问句与诊断原文来自 `sniff.cpp`，**唯一一份文案**）。

⇒ **本项目的 `check_package_fixture_pages.py` 用 rc=2 表示"未覆盖"，与此处的 2=输入不可用
  语义不同！** 这是一个**跨模块的语义冲突**，必须记下来：
  - `text::batch` 的 rc：0/1/2/3 = 成功/失败/输入不可用/需确认；
  - 判据脚本的 rc：0/1/2 = 通过/失败/**未覆盖**。
  ⇒ 同一进程里两套 rc 语义不会冲突（不同入口），但**读日志的人极易混淆**。
  我们自己的 `--smoke` 只有 0/1，判据脚本才有 2 —— 需要在交接里写清。

### 5. 钩子契约（第 131-141 行）
`should_stop` 在**文件边界**轮询（true ⇒ 停在完整产物上）；`gate` 是"让路"（暂停门/退出）；
`message` 逐条留痕；`progress(已处理, 总数)`，总数未知时 `total=0`。

★ 注意：这与 `UiFacade::TaskHooks` 同形，且**引擎在工作线程里调它们** —— 与 P17-1② 的取消位同族。

### 6. `format_duration`（第 164-165 行）
Python `str(timedelta)` 口径：`H:MM:SS`，跨天是 `N day, H:MM:SS`。

1. **"几乎恒真的判据"**（A.3 的 cp1251 闸门）—— 我们的 `layout_count>0`、`childCount>0` 属同类。
