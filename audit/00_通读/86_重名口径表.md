# 重名口径表（batch-3 的**前置契约**：先定表，再改代码）

> 2026-10-24。用户裁定：**先写表，不许边改边定**。
> 本表是 batch-3 的唯一依据；代码改动必须逐条对应到本表的行，改完把"状态"列更新。

## 一、五层行为（用户给的口径）

| 层 | 行为 | 判据 | 状态 |
|---|---|---|---|
| **`pack_db`** | **拒绝**重复路径，错误里**报出那两条原始路径** | 新包不许出现重名 | 待做 |
| **`pack_squashfs`** | **拒绝**重复路径（`build_tree` 已有 `重复条目`/`路径冲突`） | 新包不许出现重名 | ✅ 已有（补判据） |
| **parser / list**（sqfs） | **接受**，但返回 `duplicate_count` + 重复路径列表（**不静默丢**） | 读侧能看见 | 待做 |
| **parser / list**（db） | **接受**，报 `duplicate_count`（默认档） | 读侧能看见 | 待做 |
| **extract** | **确定性策略：first wins**；被忽略的那条记 `duplicate_records`；本次之前盘上已有文件记 `overwritten` | 不静默覆盖 | 待做（现状是 last-wins + 有记账） |
| **db unpack（严格档）** | 默认**接受 + 报数**；`--strict` 时**拒绝** | 老包可读、但可见 | 待做（`--strict` 是新开关） |

★ 决定"first wins"的理由：包内条目顺序是**写包时的顺序**（不是用户意图），
`last wins` 意味着"后写的赢"——那只是**打包顺序的副产物**；`first wins` 至少与"先声明者有效"这条
可解释规则一致，并且**与 `entry_paths_` 现有的 `emplace`（保留第一次插入）同向**。
★ 不论选哪个，**都必须记账**（`duplicate_records`），否则就是"静默覆盖"。

## 二、重名判定必须覆盖的五类（判定用的键）

| # | 类型 | 键怎么算 | 备注 |
|---|---|---|---|
| **D1** | 完全相同的路径 | 原样字节比较 | 最基础 |
| **D2** | 大小写不同（`A.txt` / `a.txt`） | **Windows：折小写**；其它平台：原样 | Windows 落盘会覆盖，必须算重名 |
| **D3** | 文件与目录同名 | **键里带类型**（`f:` / `d:`）⇒ 不算重名，但**要单独报冲突** | 两者在盘上不能共存；extract 现状：谁先谁赢、后到的报错（可见） |
| **D4** | 尾斜杠 / 归一化后相同（`dir\` vs `dir`） | 段末尾 `\` `/` 去掉、`\`→`/`、丢掉空段与 `.` | 与 `extract` 的 `safe_out_path` **同一套归一**（R27 的落点） |
| **D5** | Unicode NFC/NFD 变体（`é` vs `e`+组合符） | **本仓路径层不做 Unicode 规范化** ⇒ 按字节比较（**会**被当成两个不同名字） | 记一条已知缺口：Windows 上也确实可能生成两种名字；若要做，必须全链路统一，不能只在 parser 做 |

## 三、证据（为什么这些口径是安全的）

1. **真机包没有重名**：`Golden Sphere/gamedata.db_base`（11xx，5376 条目）
   - 字面相同重复组：**0**
   - 大小写折叠后重复组：**0**
   ⇒ "pack 拒绝重名"不会误伤既有语料；"extract 改 first wins"对现有语料**零字节变化**。
2. **零字节文件的 offset 不是 0**（回应 batch-2 的确认要求）：
   ```
   f  config/misc/gulag_general.ltx   0  0  493497  0
   ```
   （列：type / path / size_real / size_comp / offset / crc）
   5 条零长度文件全部 `offset=493497` ⇒ **合法的零字节文件用非零 offset 指向它的位置**；
   `offset==0` 只可能是"目录/没有数据"。
   ⇒ batch-2 那条 `!is_dir && offset==0 ⇒ malformed` **可以保留**（不是误杀零字节文件）。
   ★ 但补一句防御：若将来真遇到"零长度 + offset==0"的 xdb，它会被 `parse_xdb` 判成**目录**
   （三字段全零），所以**无论如何都不会走进"文件"分支** —— 这条规则只在"自相矛盾"的输入上触发。

## 四、实现顺序（batch-3 内部，分三个小提交）

| 步 | 内容 | 判据 |
|---|---|---|
| 3a | `pack_db` 拒绝重名（D1/D2/D4），错误列出两条路径 | 静态：错误文案含两条路径；行为：手工构造 `DbPackItem` 列表**只能靠引擎**，故加"代码级自证"或临时探针 |
| 3b | sqfs `list` 返回 `duplicate_count` + 重复路径（D1/D2） | 改镜像字节造重名 ⇒ `--dump` 输出里能看到计数与路径 |
| 3c | extract 改 **first wins** + 记账；db 侧 `duplicate_count` 进 `DbListing` | 造重名包 ⇒ 产物是**第一条**的内容、`duplicate_records` 计数为 1 |

★ 3a 的行为测试需要"能拿到引擎 API 的入口"。两条路：
  (a) CLI 加一个**只给判据用**的 `--pack-db-selftest`（造重复项，不落盘）；
  (b) 判据只做**静态 + 文案**检查，行为留给 `pack_squashfs`（已有真拒绝路径可测）。
  → **倾向 (b)**：不为了测一条判据给产品加开关；`pack_squashfs` 的重名拒绝已有行为面。

## 五、不做（本批明确排除）

- **Unicode 规范化（NFC/NFD）**：全链路统一才有效，parser 单点做只会制造"同一文件两种键"。
- **跨层共用一把"重名键"函数**：需要先定 D3（类型进键）在 UI 侧怎么显示，留给后续批次。
- **`--strict` 开关**：等 3a/3b/3c 落地后单独加（它只影响 db unpack 的处置，不动解析）。
