## A. `log.cpp`（134 行）

### 1. 两条通道，**`log_block` 只写文件**（第 72-78 行）
`log()` 写 stderr ＋ 文件（都 flush）；`log_block()` **只写文件**，注释写明
"没挂文件就什么都不做（stderr 不给：UI 行不该污染控制台）"。

⇒ **对判据的含义**：`日志长度 849 / 893` 这类读数如果来自 `log_block`（LogBox 镜像），
  它**不会出现在 stderr**，所以"看控制台有没有那行"是无效判据。必须读日志文件或 LogBox 文本。

### 2. ★ `prune_log_files` 的两处实测教训

**（a）并列时按文件名倒序兜底**（第 105-111 行）：
同一秒内的 `log_..._2.txt`/`_3.txt`、刚写出来的一批文件，mtime 精度/复制都可能抹平成同值
⇒ 只比时间的话"谁该被删"会退化成**目录迭代顺序（随机器漂移）**；
文件名就是我们自己的时间戳命名，倒序＝新的在前。

**（b）"当前这份"用两条判等的或**（第 115-122 行）：
> ★ "当前这份"用**两条**判等的或：整路径相等 **或** 文件名相等。
> 只比整路径是不够的 —— 调用方传进来的字符串与迭代器给的路径可能在不同环节被规范化
> （大小写 / 短名 / 分隔符），**我第一版只比整路径，结果把正在写的那份删了**，
> 自检当场抓出来（情形 B：deleted=1，本该 0）。

⇒ 两条都是"**比较两个路径字符串**"的坑，与我们 `path_equals` 的讨论直接相关。

## B. `path.cpp`（66 行）—— ★ 一个我读出来的**真实分歧**

```cpp
bool path_equals(...) {
    ...
#ifdef _WIN32
    const auto lower = [](char c) { return (c >= 'A' && c <= 'Z') ? char(c - 'A' + 'a') : c; };
#endif
    // 逐段比较；Windows 下每段按**ASCII 小写**比较
}
```

注释说"与 1.x 的 `os.path.normcase` 同语义"，但 **Python 的 `normcase` 走 `str.lower()`**，
那是 **Unicode 小写**（会把西里尔 `ФАЙЛ` 折成 `файл`）；这里的 lambda **只折 ASCII**。

⇒ **分歧的具体后果**：两个路径仅在西里尔/希腊大小写上不同时，
`path_equals` 判**不相等**，而 1.x 的 `normcase` 判**相等**。
影响面：`is_windows_reserved_name` 的调用方、`check_output_conflict`（`SameAsSource` 判定）、
`pack_db` 的"输出撞输入"守卫 —— **全是"会不会覆盖源文件"这类安全判定**。

★ 本项目的实际语料路径以 ASCII 为主，所以一直没炸；但这是**可判定的分歧**，
应当：
1. 要么按 Unicode 小写实现（用 `case_fold.h` 的 `case_fold_lower`，`src/core` 不依赖 `engine` 就自己写）；
2. 要么在注释里**如实写成"只折 ASCII"**（现在的注释说"与 normcase 同语义"，是**过强**的断言）。

⇒ 这正是本仓最看重的那类问题：**注释的断言比实现强**。

## C. `atomic_write.cpp`（272 行）—— 写盘纪律的完整实现

### 1. 为什么是 FNV-1a（第 20-31 行）
这条校验要拦的是**我们自己的写路径 bug**（长度截断、偏移错 1、缓冲区接错），
**不是对抗性伪造** ⇒ FNV-1a 足够、5 行、不引依赖；长度另有一条**独立判据**
（实际写出字节数 vs `data.size()`），两者合起来覆盖"写错长度"与"写错内容"。

★ 并且说明：两个方向（内存那份、写出的那份）**共用同一个函数** —— "不自洽的风险就此消掉"。

### 2. ★ `remove_with_retry`（第 50-73 行）：实测抓到的真缺陷
Windows 上 `stdfs::remove` 会**因为句柄还没落定而静默失败**（`error_code` 非零但没人看）
—— 同一进程里刚动过那个文件的句柄（例如探针的 `fstream`）会挡住它一小会儿。
原来一行 `stdfs::remove(temp, ec);` **丢了返回值**，于是"解包失败还留一个 `.part`"**谁也看不见**。
⇒ 短重试（50 × 2 ms）＋ 最终失败写进 `error`。

### 3. ★★ 第 132-135 行：又一次**自我更正**
> ★ 2026-09-27 更正（我自己的实测）：**俄文在 CP936 下能无损编码**（`файл` → `a7e6a7d1a7dba7dd`）；
>   真正会退化成 `?` 的是 **CP_ACP 表示不了的字符**——韩文、日文假名、emoji、Ё 等。
>   早先注释写"俄文会变 ?"是错的，**别再照它复刻**。

⇒ 这条与 `untrusted_limits.h` 的 P17-115 更正、`log.cpp` 的"我第一版只比整路径"是同一族：
  **本仓把"我错过什么"写在代码里**。这是我最该学的做法 —— 也让"读注释信以为真"的风险降低。

### 4. T-03 的诚实口径（第 238-259 行）
补一次 `file_size(temp)` 比对（一次 `stat`），但措辞明确：
买到的是「**检测并明确报错**」不是「**防止**」；本档**没有** FlushFileBuffers/fsync
⇒ **不承诺断电/崩溃场景**。

### 5. 探针的三个注入口互不混用（第 143-198 行）
- `tamper_expected_hash`：只改**比对用的期望值**（真实输出不动）；
- `truncate_temp_file`：写完后把临时文件**截短 1 字节**（模拟落点短写），**两档都触发**；
- `tamper_temp_file`：**只在 `Readback` 档触发**（流式档不读回，动了它自检就自相矛盾）。

⇒ "**两条锁各用各自的注入口**"这条纪律（`include/.../atomic_write.h:47-57`）在这里落地。

## D. 这三份文件给"红点"的可执行结论

1. **`path_equals` 只折 ASCII**（B 节）：如果我们有"输出撞输入"的判据依赖它，
   在西里尔大小写不同的路径上会**漏判**。→ 可写入待办（严重度中：目前语料多为 ASCII）。
2. **`log_block` 不进 stderr**（A.1）：日志类判据必须读文件/控件，不能读控制台。
3. **"注释比实现强"是可判定的缺陷**（B 节末）：下次改代码时，优先把过强断言改弱/改准，
   而不是让它继续误导下一个人。
