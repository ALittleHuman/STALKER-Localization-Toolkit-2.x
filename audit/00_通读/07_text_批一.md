## A. `encoding.h`（105 行）

### 1. ★ 两条链**不是一条**（第 4-7 行）
- **六编码链**（文本提取页用，本文件）：`utf-8-sig → utf-8 → gb18030 → windows-1251 →
  windows-1252 → latin-1`，前五种**严格**解码，末位 latin-1 兜底（所以**永不失败**）；
- **判定链**（编码转换页，`sniff.h`）：六步判定。

⇒ **判据必须知道自己在测哪条链**。我们之前在 P12c-2 / 日志那条上看到"日志长度 849/893"这类
  抖动，若涉及编码，先确认走的是哪条。

### 2. ★★ 严格性是**语义**，不是细节（第 9-11 行）
cp1251 的 `0x98`、cp1252 的 `0x81/0x8D/0x8F/0x90/0x9D` 在 Python 里都抛 `UnicodeDecodeError`。
若把它们当 U+FFFD 放行，"windows-1251"这一步会**错误地解成功** ⇒ 整条链的落点从 latin-1
变成 cp1251 ⇒ **解码结果直接变**。

⇒ 这是"**宽松处理 ⇒ 判据落点漂移**"的经典。**任何"容错"都要问：容错之后，下游还能分辨吗？**

### 3. ★ ALPHA.44 的真缺陷（第 37-40 行）：`ascii` **只有解码侧**
"连纯 ASCII 正文都被整篇写成 `?`" ⇒ 那批的判据包含"**能被编码**"。
⇒ **能力必须两侧都测**（decode + encode），只测一侧就会漏掉半个实现。

### 4. 有损模式（第 63-74 行）：语义必须**逐项对拍**
- 解码方向：坏字节 → U+FFFD，个数按 CPython 的"最大子部分"规则
  （实测：`e4b8`→1 个、`e4b8e4`→2 个、`e08080`→3 个、`e441`→1 个 + `'A'`）；
- 编码方向：目标编码表示不了的码位 → `?`；
- **尚未对拍的编码（utf-16/utf-32 家族）返回 false 并说明，不假装支持。**

⇒ "不假装支持"这条是零静默的另一面：**宁可不支持，也不给半对的结果。**

### 5. `read_text_file` 含**通用换行归一**（第 79-85 行）
Python 文本模式默认 `newline=None`，会把 `\r\n` 与 `\r` 都翻译成 `\n`。
注释原话：漏了这一步，"编码名对了、正文也对了"的假象下，凡用 `\r\n` 的源文件都会对不上。

⇒ **对拍必须连"换行归一"一起对**，否则永远差一点点 —— 这类"差一点点"最难查。

### 6. `codec_encode_table(which)`（第 97-103 行）：为"能进门禁"而设计的接口
逐条核对反向表要 ~2.9 万次进程启动（每次 15ms ⇒ 十分钟级），塞不进门禁
⇒ 整表导出把"逐项核对"压成三次调用。

⇒ **这是"判据可行性"驱动的 API 设计**：判据跑不动的检查，等于没有检查。
  我们的 30 次 soak 也是同一问题（每次 ~40s × 30 = 20 分钟），所以必须**分级**。

## B. `convert.h`（134 行）

### 1. 逐条照抄 1.x `convert_app.convert_file`（第 4-12 行）
- 入口先剥 BOM，但**剥掉不等于忘掉** —— "源带 UTF-8 BOM"这个事实要用标志传下去
  （输出侧一律不带 BOM，BOM 只对 utf-8 合法，留在 cp1251 文件里是脏字节）；
- 解码用 `errors="replace"`（**不是严格解码**）；
- 写盘 `newline=""` ⇒ **不做任何换行翻译**（与 `read_text_file` 的归一正好相反！）；
- 目标编码 `errors="replace"`：表示不了的码位写 `?`；
- `.xml` 走 `_fix_xml_decl`：统一双引号 + **只替换已存在的 encoding 属性**；
- 源编码 == 目标编码时走**对齐分支**（`needs_rewrite`），不是简单不写。

★★ **注意这条内部矛盾（有意为之）**：读侧归一 `\r\n → \n`，写侧**不做**翻译。
⇒ 一次"中转"确实会把 CRLF 变成 LF。这是 1.x 的行为，2.0 照抄。**判据必须按这个口径**，
  不能想当然以为"往返相等"。

### 2. ★★ P17-87：**编码判定一律要问，不许自动模式**（第 52-64 行）
用户原话：「**全部上模态对话框。谁让你这么喜欢用自动模式的？**」
- GUI：每一次编码判定都上**模态**、用户显式确认；**不设**"页内建议/自动通过/静默按 auto 继续"；
  用户**取消或关掉 = 不继续**；
- CLI/headless：没有窗口 ⇒ **不许猜** —— 问句与诊断**原样报出** + **非零退出**；
- **只对 `auto` 触发**（手动指定了源编码就不再问，否则"选择"本身没意义）。

为什么钩子在引擎：引擎不许碰 Qt（门禁 `no-qt` + `check_no_qt.cmake` 锁着），
而页面那条路**不覆盖批处理/CLI** ⇒ 只有"宿主注入回调"这一种形状能同时满足两侧。

⇒ **这是"能力必须在两层都成立"的又一例**（与 registry 的 CLI/GUI 分叉同族）。

### 3. ★★ T-08：取消是一等公民（第 117-121 行）
修前：`user_cancelled` 不存在，取消只能靠 `error` 文案去认（"改文案＝改语义"的老坑，
C-02 同族）；且取消只否决当前这一份，**后面 499 个照样逐个弹窗**。
现在：`user_cancelled` 是具名字段，批处理靠它**停下整批**。

### 4. ★ `used_mismatch`（第 109-113 行）：静默回退必须报出来
转换路径原来有一处**静默回退**：判定编码 `decode_lossy` 失败就悄悄改用 windows-1251
（1.x 也这么做，但至少记一条警告）。现在既记 flag 也计数。

⇒ **"回退"是一种必须被看见的行为**。我们判据里的"重试/兜底"同理。

### 5. `ConvertOutcome` 的字段分类（第 90-122 行）—— 一个值得抄的模板
```
ok / skipped / wrote        ← 三态（不是 bool 一键判断）
needs_confirm + question    ← "需要人决定"是具名状态（P17-122 同族）
step/step_label/source_encoding/used_encoding/used_mismatch  ← 判定事实
flags_label/confidence/low_confidence/override_decl          ← 置信度可见
user_cancelled              ← 取消是事实（T-08）
error                       ← 只表示"失败"
```

⇒ **这正是我们缺的东西**：`settle`/`page_ready` 目前只有 `anything=0/1` 加一堆 note；
应该升级成"三态 + 具名事实 + 失败原因"的结构。
