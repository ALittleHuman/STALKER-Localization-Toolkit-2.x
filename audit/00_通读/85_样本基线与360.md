## 四、需要你裁定的一件事（我不动基线）

`golden-text-decode` 的 2 个 real 样本与基线不符。三种处置，**都要你点头**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 把这两个样本**冻结**成副本（换到 `samples/` 下一个只读目录），decode 指向副本 | 基线不动、判据仍有效；多一份 ~小文件副本 |
| B | `--write` 重记这两条的基线 | **改基线**：以后就测不出这两个文件的漂移了 |
| C | 维持现在（release 红） | 每次 `--release` 都红在这一条（已知、可解释） |

★ 我倾向 **A**：你正在做普里皮亚季编年史的汉化，这些 xml 很可能就是**你在改的文件**；
  把"判据用的样本"和"你手里的工作副本"分开，两边都不互相拖累。

## 六、★ 结论（2026-10-24 13:2x）：**没有内容漂移，`stale=2` 是指纹错位的假红**

### 6.1 根因（Hana 的猜测对了一半，我查证后落到了具体代码）

`golden_text_decode.py` 的 `real/<序号>_<名字>` 里**序号是位置序**（`:191-196` 的注释自己就写了），
而兜底匹配只按 **basename**（`base_by_name[sid.split("_",1)[1]]`）⇒ 两个真实缺陷叠加：

1. 任何语料树不可达 ⇒ 后面所有 id **整体前移**；
2. 兜底按名字 ⇒ **同名不同文件**被当成同一份：实测 `XR_3DA.exe` 有两份
   （`bin\XR_3DA.exe` 1636424 B / `bin\dedicated\XR_3DA.exe` 1599560 B，基线里 id 是 142 与 129），
   当前第 69 号那个文件被拿去和**另一份**的哈希比 ⇒ 报"内容变了"。

### 6.2 修法（最小、可判）

兜底改成 **名字 + 尺寸**：同尺寸不同哈希才算**真漂移**（`stale`）；尺寸不同 ⇒ **是另一个文件**（`denied`，
"语料集变了"，进未覆盖）。三处改动都在 `golden_text_decode.py` 的匹配段。

### 6.3 结果

```
修前：GOLDEN-TEXT-DECODE: PARTIAL (compared=103 failed=0 stale=2)   ← 假红
修后：GOLDEN-TEXT-DECODE: PASS   (compared=105 failed=0 stale=0 denied=0)
run_ci.py --release → RESULT: PASS（exit 0）        ★ 全档绿
```
