## 0-1 `--release --only <一步>` 直接 PASS 却谎称"全部步骤均已执行"

- 位置：`tests/run_ci.py` `main()` 的步骤循环 + 收尾覆盖度摘要（修前 `:1760-1789`）
- 机制：`--only` 过滤掉的步骤**既不记账也不进未覆盖清单**；收尾 `if UNCOVERED: … else: 打印"本次覆盖：全部步骤均已执行"`
  于是无条件打印后者 ⇒ 只跑 1/36 步也自称全覆盖，且 release 档照样 `RESULT: PASS`。
- 修法：① `--only` 与 release 互斥（显式说明）；② **跳过的步骤逐条记入 UNCOVERED**。

#### 红（修前）—— 命令与原始行
```
python tests/run_ci.py --release --only px-only
```
```
[px-only] 像素口径：尺寸/间距只许过 px()
  PX-ONLY ok 尺寸/间距一律过 px()（白名单 1 条：log_box 的 1px 布局技巧）
  ok   尺寸/间距一律过 px()（屏幕自适应口径）
------------------------------------------------------------------
本次覆盖：全部步骤均已执行
------------------------------------------------------------------
RESULT: PASS
=== exit code: 0 ===
```

#### 绿（修后）
```
python tests/run_ci.py --release --only px-only
```

## 0-2 release 的"未覆盖清单非空 → FAIL"是死分支

- 位置：`tests/run_ci.py` 收尾 `if release and UNCOVERED: FAILURES += 1`（修前 `:1782`）
- 机制：release 档下 `prereq()` 走 `fail(); return False` 分支**不 append**（`:125-132`）；
  另一处 `UNCOVERED.append` 在 `step_cli_contract` 的一个**空元组循环**里（`:338-339`）。
  ⇒ 在 `--only` 修好之前，release 档下 UNCOVERED **必然为空**，该判据永不触发。
- 修法：**不改判据**，而是给它一个活的写入者 —— 0-1 的"按 `--only` 过滤掉的步骤逐条进 UNCOVERED"。
  该分支因此变成唯一把 release 判红的通道（0-1 的绿就是这么来的，见上 `RESULT: FAIL`）。

#### 红（修前）：该分支永不执行
- 证据：`--release` 整跑时 `prereq` 只走 `fail()` 不 append；唯一另一处 append 在空元组循环里。
- 因此 `--release --only px-only` 修前能 PASS（见 0-1 红），即该判据是死的。

#### 绿（修后）：`--release --only px-only` 由该分支判红
```
release 档：未覆盖清单非空 → 整体 FAIL
RESULT: FAIL（1 处失败）
```

## 1-2 `db.cpp read_chunks` 判据漏 `pos`（堆越界读）+ `long` 32 位截断

- 位置：修前 `src/engine/fs/db.cpp:404-407`
  ```cpp
  if (cid <= 1 && 8ull + sz <= raw.size() && sz > 0) {
      const bool comp = (rid & 0x80800000u) != 0;
      std::vector<uint8_t> data(raw.begin() + static_cast<long>(pos + 8),
                                raw.begin() + static_cast<long>(pos + 8 + sz));
  ```
- 机制（**静态确认**，见"复核"一节的口径说明）：判据用 `8+sz`、切片起点用 `pos+8`
  ⇒ `pos>0` 且 `8+sz <= size < pos+8+sz` 时末端越过 `raw` 末尾；`static_cast<long>`
  在 Windows x64 是 32 位 ⇒ `pos+8+sz > 2^31` 截断成负值 ⇒ 野指针。
- 修法：判据与切片起点**同源** —— `pos + 8ull + sz <= raw.size()`（`8ull` 保证前两项
  在 uint64 域相加不溢出），切片改用 `std::ptrdiff_t`，并留一条不变式注释。
- 绿：`--dump` 在既有夹具上行为不变（`tests/golden_db.py` / `golden-extract` 等步骤照旧全绿，
  见下方门禁两行）；新增的 `read_chunks` 边界注释与不变式已落地。
- ★ 复核说明（不夸大）：**未**在本批做运行期越界取证 —— 退回整文件读那条路的可达前提是
  "seek 路径认不出"（`db.cpp:770-789`），本批用 1 字节前缀/假块头/超大 sz 三种夹具实测
  `--dump` 仍走 seek 路径（`seek=1`），因此**没有**造出一个能在 `%TEMP%` 里跑出 ASan 红的样本；
  本条的"红"是代码级（判据与切片起点不同源）＋ 审计 §1 S1-5 的独立复现，如实记在这里。

## 3-5 `xml_page.cpp:435` 在工作线程里刷 `QTreeWidget`

## 补充 H1-5 / 用户裁决：包内自检入口曾因缺离屏平台插件**崩 0xC0000409**（留痕）

> 这条是 2026-10-07「不在 §7 分组里」那一批自查出来的**存量**事实；用户当天裁决：
> **部署舞台必须同时带 `qwindows.dll` 与 `qoffscreen.dll`**，并把判据写进包内 README 与门禁。

- 现象（可复现）：拿**包内**的 `xrkit_app.exe` 跑 `--smoke`（`QT_QPA_PLATFORM=offscreen`）
  ⇒ 退出码 `0xC0000409`（`-1073740791` / `3221226505`），stdout/stderr **一个字节都没有**。
  WER 签名：`Application Error` / `BEX64` / 故障模块 **`Qt6Core.dll`** / `P7=0x267a8`。
- 复现命令（在包目录里，别在 build 目录里）：
  `set QT_QPA_PLATFORM=offscreen && dist\2.0.0\ALPHA\59\xrkit_app.exe --smoke`
- 排除过程（全部实测）：
  1. 包内 `xrkit_app.exe` 与 `build\msvc-shell\src\shell\xrkit_app.exe` **SHA256 完全相同**
     （`9528367337DB78C346F3361BCCFFE2E4EE915CF9814549BE00B93B4D7E52C25D`）；
  2. `Qt6Core.dll` / `platforms\qwindows.dll` 与 Qt 6.8.3 官方 bin **逐字节相同**；
  3. **同一个 exe** 在 `build` 目录、以及把 `build` 目录整体复制到 `%TEMP%` 后再跑，都
     `SHELL-SMOKE ok checks=753 failed=0`；
     ⇒ 差别只在**目录内容**，不在二进制。
  4. 差异定位：`build` 目录的 `platforms\` 有 `qwindows.dll` **与 `qoffscreen.dll`**，
     而包内**只有 `qwindows.dll`**（`package.ps1` 修前是"跑判据前临时拷、跑完在 `finally`
     里删掉"，注释自述"保持包精简"）。
  5. 定性验证：给同一份包布局补上 `qoffscreen.dll` ⇒ `SHELL-SMOKE ok checks=713 failed=0`。
- 存量性：`ALPHA.57`、`ALPHA.58`、`ALPHA.59` 三个包**同一签名同一崩溃**（`P7=0x267a8`）⇒
  **不是某一批引入的**，而是"包内自检入口"一直不可用（正常双击使用不受影响）。
- 修（用户裁决）：`scripts\package.ps1`
  · 部署舞台**拷入并保留** `platforms\qoffscreen.dll`（109 KB）；
  · 产物侧断言：`platforms\` 里 `qwindows.dll` + `qoffscreen.dll` **都要在**（`Test-Path`，缺即 throw）；
  · 结论行判据收窄：从"只 grep `SHELL-SMOKE ok`"改成 **`SHELL-SMOKE ok checks=(\d+) failed=0`**
    且退出码 0 —— 修前那个写法会把 `SHELL-SMOKE ok checks=741 failed=1` 读成**通过**
    （本批实测见过这一行，属于同族假判据）；
  · `version.txt` 增契约声明行 **`platform_plugins=qwindows,qoffscreen`**：门禁据此对
    **声明过的序号**执行"两份都在 + 从产物目录真跑 `--smoke` 要求 `failed=0`"；
    修前打的旧序号没有这一行 ⇒ 门禁记**台账**（不阻断），声明了就必须成立。
- 门禁判据：`tests/run_ci.py` 新步 **`[pkg-platform]`** → `tests/check_package_platform.py`：
  ① 静态（`package.ps1` 拷/不删/断言/`failed=0`/契约声明，含两条自证"喂反例必红"）；
  ② 产物（声明过的包：两份插件在 + 真跑一次）；③ 没有带声明的新包 ⇒ 台账。
  ★ 判红办法：把 `package.ps1` 里拷 `qoffscreen` 那两行删掉（①红），或把 `failed=0` 放宽回
  只 grep `ok`（①红），或删掉包内 `platforms\qoffscreen.dll`（②红）。

## H1-2 版本号只许一份真来源（用户 2026-10-07 拍板"候选 A"）

- 位置：`include/xrkit/core/version.h:16,19`（`kPrerelease="ALPHA.0"` / `kBuildCount=0`）、
  `src/core/build_version.{h,cpp}`（写回/回滚）、`tools/cli/build_cmd.cpp`（写回点）、
  `tools/cli/main.cpp`（`--version-store … write-header`、`--exe-version`）、
  `scripts/package.ps1`（包内 exe 身份断言）、`tests/check_version_identity.py`（判据）。
- 机制（修前）：**两个"唯一事实来源"且无任何比对** —— exe 的资源与 `core::version_string()`
  编自 `version.h` 的常量（那两行**从来没被写回**过），而包目录名 / `version.txt` 来自
  `version.json`；既有两条锁（`.rc ↔ version.h`、exe 资源 ↔ `core::version_string()`）
  **都在各自源内自比** ⇒ 全绿。
- **红（修前，原始行；对**同一个交付物**）**：
  ```
  $ xrkit_cli --exe-version dist\2.0.0\ALPHA\60\xrkit_app.exe
  EXEVERSION product=2.0.0 ALPHA.0 file=2.0.0 numeric=2.0.0.0 path=dist\2.0.0\ALPHA\60\xrkit_app.exe
  $ type dist\2.0.0\ALPHA\60\version.txt
  version=2.0.0 ALPHA.60
  ```
  把**修前的真实文件**喂给本批的分析器（同一批函数，能判红）：
  ```
  ① 修前 version.h  -> ['version.h 的 kPrerelease=「ALPHA.0」≠ tree 现算的「ALPHA.60」',
                        'version.h 的 kBuildCount=0 ≠ tree 的最后一次发包序号 60']
  ② 修前 .rc        -> ['.rc 的 ProductVersion=「2.0.0 ALPHA.0」≠ 期望「2.0.0 ALPHA.60」',
                        '.rc 的 FILEVERSION 第 4 段=0 ≠ 序号 60']
  ③ 修前包内 exe    -> ['exe 的 ProductVersion=「2.0.0 ALPHA.0」≠ 期望「2.0.0 ALPHA.60」',
                        'exe 的数值版本=「2.0.0.0」↛ 第 4 段应为 60']
  ```
- 口径（用户拍板）：**真来源 = `version.json` 的 tree**（最后一次成功发包）；`version.h` 是
  **派生**（`kPrerelease="<标记>.<序号>"`、`kBuildCount=<序号>`）。写回点 = `--build-package`
  写 `version.json` 之后、调 `build.ps1` **之前**（exe 的资源和 `version_string()` 都编自
  version.h）→ 紧接着重跑 `tools/gen_winres.py` 让 `.rc` 同源；失败路径复用既有
  `restore_version_store` 并**把 `version.h`/`.rc` 一起回滚**（按原字节写回 + 读回校验）
  ⇒ **序号不被吃掉**。写回走 `write_file_atomic`（**原子写**）+ 写后读回校验。
- 判据（新独立步 `[version-identity]` → `tests/check_version_identity.py`）：
  ① `version.h` ↔ tree（期望值**从 tree 现算**，不写死串；**不读 `current.index`**
  ——它是"下一个号"，门禁与构建 GUI 都会推它，实测 59→60）；
  ② `assets/xrkit_winres.rc` ↔ `version.h`（ProductVersion + FILEVERSION 第 4 段）；
  ③ **包内 exe** ↔ `version.txt`：判据**自己用 ctypes 直读 exe 的 VERSIONINFO**（不信任
  `version.txt` 的自报），仅对 `version.txt` 里声明了 `exe_identity=` 的序号执行
  （修前打的旧序号记台账——它们确实对不上）；④ 三条自证（假 version.h / 假读数 / 旧形态 .rc）。
  ⑤ **打包链自己的判据**：`package.ps1` 从**产物**读 `xrkit_app.exe` 的真实版本资源，
  与本次发版串逐字比，不一致就 throw（包根本不落地），一致才写 `exe_identity=`。
- ★ 判红办法：改 `version.h` 的 `kBuildCount`（①红）；手改 `.rc`（②红、且门禁 `.rc --check` 也红）；
  把包内 `xrkit_app.exe` 换成旧构建的（③红）；把 `--build-package` 里的写回段删掉再发包
  （③红且 package.ps1 直接 throw）。
- ★ 踩到的两个坑（如实登记）：① 用 `edit` 工具改 `scripts\package.ps1` 会**抹掉 UTF-8 BOM**
  ⇒ PowerShell 5.1 按 GBK 读、门禁 `[1]` 的 BOM 判据直接红（本批门禁首跑就是这么红的）；
  改完必须补回 `\xef\xbb\xbf` 并用 `[System.Management.Automation.Language.Parser]::ParseFile`
  自证；② ctypes 读 VERSIONINFO 时，串值的 `puLen` 是**字符数**（不是字节数），而
  `VS_FIXEDFILEINFO` 的 FILEVERSION 在**偏移 8**（前 8 字节是 Signature+StrucVersion）
  —— 按"字节数 + 偏移 0"读会得到 `2.0.0 A` / `65263.1213.1.0` 这种**看着像真读数**的假数据。
